## 1. 방법
### 1.1 사용 빈도 (얼마나 자주 쓰이나)
`tools/gto_precision/spot_usage_sim.py <fmt> <day> <out>`: test3 코드 그대로(이 브랜치 = test3 a090dde), 실제 예약 대회 경로(`scheduled_runtime.advance`), 표준 프로필, 봇만, 고정 시드.

gto_pf 의 보간 규칙 그대로(버킷 사이 직선 보간 몫, 오픈 2.0/2.5 표 사이 몫) 기여한 기록에 나눠 준다.

### 1.2 불안정 (얼마나 못 믿나)
- 기록에서(`record_instability.py`): 뿌리 노드(연결에 쓰는 노드)의 `unstable_combos / reach_combos`(단계 사이 클래스 빈도가 10%p 넘게 움직인 콤보 몫),
  `ev_loss_of_mean_vs_each_step_bb` 최댓값, 0.2~0.8 로 섞인 콤보 몫, 클래스 gap 가중 평균, 수렴 여부.
- 계산 브랜치에서(`collect_step_du.py`, 16개 브랜치, 43개 spot): 단계별 끝점 D/U(= 이번 단계 끝점 값 변화 / 패널 허용폭) 최댓값. 루프 기준은 모든 끝점·자리 D/U ≤ 1.
  22개 기록(대부분 30bb 플랫, 30bb·40bb 일부 3벳, SB 림프)은 단계 보고를 브랜치에서 못 읽었다(보관 브랜치의 tar 안) → "자료 없음", 점수에서 0 처리.
- 걸음 사이 클래스별 최대 변화량은 기록에 걸음별 전략이 없어 >10%p 표시만 쓸 수 있다.

### 1.3 점수
`risk = 0.05(바닥: 24보드 quick, 검증 없음) + unstable_share + 0.05 × min(4, max(0, 마지막 D/U − 1))`, 부모 트리는 0.05(솔버 gap ≤ 0.01bb).
`impact = 1000핸드당 사용 수 × risk`. EV 손실은 점수에 넣지 않고 같이 보인다. 가중치는 임의로 정했다 — 순위가 바뀌는지 보려면 JSON 의 원 지표로 다시 매기면 된다
(unstable_share 만 쓰면 같은 다섯, 순서만 바뀜. 마지막 D/U 만 쓰면 100bb·60bb HJ 대신 수렴한 60bb CO·100bb BTN o25 가 들어온다 — 많이 쓰이고 D/U 0.76·0.95 로 경계라서다).

## 3. 정밀(precision) 표준 초안
quick 은 "24보드 패널 하나, D ≤ U 이거나 3단계에서 멈춤"이다. 사용자 지적대로 D ≤ U 만으로는 부족하다: 패널이 층(stratum) 12개 × 2보드라 U 자체가 불안정하고,
U 에는 솔버·모델 편향이 없으며, 패널이 시끄러울수록 U 가 커져 오히려 쉽게 통과한다(실측: 3벳 기록의 U 0.45~1.0bb, 플랫 0.27~0.39bb — 3벳 쪽이 더 쉽게 "수렴").

| 항목 | quick (지금) | precision (제안) |
|---|---|---|
| 패널 | panel_v1 24보드(12층 × 2) | **A·B 두 독립 패널, 각 72보드(12층 × 6, 다른 시드, 겹치지 않음)**. 합치면 144(지금 panel_v3_144 와 같은 크기지만 그건 24보드를 포함한 중첩 패널이라 독립 복제가 안 된다) |
| 통과 조건 | 모든 끝점·자리 D ≤ U(24) | ① A∪B 로 D ≤ U(144) **그리고** ② 복제: 끝점 값 \|V_A − V_B\| ≤ 2·√(U_A² + U_B²) 이고, 뿌리 전략이 A만·B만으로 풀었을 때 클래스별 차이 ≤ 5%p(콤보 가중 95% 이상) |
| 단계 | 최대 3단계, 못 끝나면 마지막 2단계 평균 | 24보드 최종 상태에서 시작, 144보드로 최대 3단계(감쇠 0.5). 순환(D/U 가 줄지 않고 오르내림, 예: 40bb CO o25 1.74→1.92)이면 그 끝점만 CFR+ 재시도(승인된 방식) 또는 감쇠 0.25. 그래도 안 되면 precision 실패로 표시하고 quick 값 유지 — **평균을 precision 이라 부르지 않는다** |
| 솔버 | 플랍당 목표 0.3~0.6% pot, 넘으면 예외 | 같은 목표. 서브게임 exploitability(bb)를 **D/U 와 따로** 보고(`u_solver`), 0.01bb 이하. 목표를 넘긴 플랍 목록과 그 몫을 기록에 남긴다 |
| 빈도 등급 | 없음(`unstable_across_steps` 표시만) | `grade_spot.py` 그대로: 클래스마다 u = u_panel + u_outer + u_solver, gap > 2u 이면 `stable`(빈도 신뢰), 아니면 `near_indifferent`(빈도 대신 "무차별 묶음"). u_outer = 마지막 두 단계 gap 차이. precision 에서는 u_panel 을 A∪B 로, 그리고 **u_rep = \|gap_A − gap_B\|/2 를 더한다**(패널 표본이 U 를 과소평가하는 경우를 잡는다) |
| 기록 상태 | `quick` | 위를 모두 통과 → `precision`(stable 콤보 몫도 같이 적음). 일부 실패 → `quick` 유지 + 실패 이유. DB 승격 금지는 그대로 |
| 연결 | quick 값 | precision 값으로 교체할 때는 지금 연결 절차(검사 + 회귀 + 화면 + 레인지 동기화) 그대로, 바뀐 클래스 목록을 같이 보고 |

남는 한계(정밀로도 안 없어지는 것): 대칭 스택, chip EV(ICM 없음), 부모 트리의 간이 플랍 모델(2.3절), 3벳 크기 두 개 → 하나로 합친 연결.

## 4. 비용 추정 (계산 안 하고 로그로)
- 근거: `docs/GTO_RESUME_40BB.md`(census 브랜치) "한 단계 ≈ 3시간(끝점 3개 × 24보드, 일꾼 4)" → **끝점 하나·24보드·1단계 ≈ 1시간**(4코어 컨테이너 기준). 보드 수에 비례한다고 본다.
  끝점 수: BB 플랫 수비 3개(100bb 는 5개), 3벳 받은 오프너 2개(단계 보고에서 셈).
- precision 1단계(144보드 = A72 + B72): 끝점당 6시간 → **BB 수비 18시간, 100bb BB 수비 30시간, 3벳 12시간.** 등급 매기기(spot 재풀이)는 분 단위.
- spot 당: 수렴했던 기록은 보통 1단계(복제만) = 12~30시간. 미수렴 기록은 최대 3단계 = 36~90시간 + CFR+ 재시도 약 10%.
- 1~5순위(모두 미수렴): 100bb 둘 × 90 + 40·60bb 셋 × 54 ≈ **340 컨테이너 시간**(4코어 컨테이너 하나로 약 14일, 다섯 컨테이너로 3~4일). 각 spot 1단계만 먼저 하면(복제 결과로 더 갈지 결정) 30+30+18×3 ≈ 115시간.
- 운영 비용: 백그라운드 작업 2시간 제한 → 단계마다 재시작·백업(기존 `plan_a_backup_progress.sh` 방식). 100bb 플랍이 더 느린지는 로그에 시간이 없어 확인 못 함.
