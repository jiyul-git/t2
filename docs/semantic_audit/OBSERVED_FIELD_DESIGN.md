# 관찰 기반 필드 진행 설계 (초안, 2026-10-06)

상태: **설계 초안 — 사용자 승인 전. 코드 없음.**

## 1. 왜 필요한가

예약 대회의 봇 필드를 실제 봇 엔진으로 끝까지 진행하면 비용이 커진다
(실측: 100명 standard 한 대회 CPU 약 20분, 대회 시작 직후 0.2~0.45코어 상시 사용).
또한 서버가 꺼져 있던 구간을 따라잡느라 레이트 바이인이 몇 분씩 걸린다(CI 480.8초).
사용자가 늘수록 사람 한 명당 쓸 수 있는 서버 자원은 줄어든다.

한편 사람이 보지 않는 테이블의 핸드 내용은 아무도 보지 않는다. 사람이 보는 것은
로비의 순위·남은 인원·평균 칩·진행 시간과, 자기가 앉은 테이블뿐이다.

## 2. 원칙 (변경 시 사용자 승인)

1. **실제 진행(real)이 기준이다.** 통계 진행(coarse)은 실제 진행을 흉내 내는 근사이고,
   실제 진행과 분포가 같다는 검증(§7)을 통과해야만 켤 수 있다.
2. **떼었다 붙일 수 있다.** 진행 방식은 하나의 경계(§4) 뒤에 숨는다. 설정 하나로 전부 실제
   진행으로 되돌릴 수 있고(킬 스위치), 그때 다른 코드는 바뀌지 않는다.
3. **관찰되는 곳은 항상 실제다.** 사람이 앉은 테이블은 언제나 실제 봇 엔진으로 진행한다.
   통계 진행은 사람이 보지 않는 테이블에만 쓴다.
4. **봇 엔진은 건드리지 않는다.** 통계 진행은 별도 파일이고 봇 결정 코드를 부르지도 바꾸지도
   않는다. R2 기준선(e04c7e88/6dc97c62)은 어떤 모드에서도 불변이어야 한다.
5. **상태는 하나다.** 두 방식은 같은 필드 상태 형식(선수별 칩, 테이블, 탈락 순서, 레벨,
   가상 시각)을 읽고 쓴다. 로비, 상금, 입장, 지갑 코드는 어느 방식인지 모른다.
6. **기록은 숨기지 않는다.** 대회마다 어느 구간이 실제였고 어느 구간이 통계였는지 남긴다.

## 3. 용어

- **관찰된 테이블**: 사람(HERO)이 앉아 있는 테이블. 이후 관전·다인 플레이가 생기면
  그 테이블도 포함한다.
- **실제 진행(real)**: 지금의 `scheduled_runtime.advance` + 봇 엔진.
- **통계 진행(coarse)**: 핸드마다 봇 결정 없이 확률 모델로 칩 이동·탈락만 굴리는 진행.
  선수 한 명 한 명의 칩과 탈락 순서가 실제로 존재한다(집계만 움직이지 않는다).

## 4. 구조

```
field_backend.py      경계. advance(event, target) 하나만 바깥에 보인다.
  ├─ RealBackend      지금의 scheduled_runtime.advance 를 그대로 감싼다.
  └─ HybridBackend    관찰된 테이블은 RealBackend 의 테이블 계산,
                      나머지 테이블은 coarse_sim 으로 진행하고 같은 시간순 병합을 쓴다.
coarse_sim.py         통계 진행 모델(새 파일). 봇 엔진을 import 하지 않는다.
coarse_params.json    보정값(§6). 실제 진행 측정에서 만든다.
```

- **모드 선택**: `T2_FIELD_BACKEND=real|hybrid` (기본 `real`).
- **모드 고정**: 대회가 시작될 때의 모드를 그 대회의 rules 에 고정한다. 진행 중에 서버 설정이
  바뀌어도 그 대회는 처음 모드로 끝낸다. 섞여서 일관성이 깨지는 것을 막는다.
- **킬 스위치**: `real` 로 되돌리면 새 대회부터 전부 실제 진행. 이미 hybrid 로 시작한 대회는
  hybrid 경계로 계속한다(상태 형식이 같으므로 실제로 이어 받아도 동작은 한다).

## 5. 넘겨받기 (coarse → real)

- 사람이 테이블에 앉는 순간(레이트 바이인, 재참가, 테이블 이동으로 도착), 그 테이블은 다음
  핸드부터 실제 진행이다. 봇의 성향·프로필·틸트·상대 기억은 필드에 그대로 있으므로 이어진다.
  통계 구간에서 바뀐 것은 칩·좌석·탈락뿐이다.
- 사람이 테이블을 떠나면(탈락, 이동) 그 테이블은 다시 통계 진행으로 돌아간다.
- 넘겨받기는 완료된 핸드 경계에서만 한다(지금 입장 규칙과 같다).
- 레이트 바이인 대기: 통계 진행은 핸드당 마이크로초 수준이라 "지금"까지 즉시 따라잡는다.
  목표 3초 이내.

## 6. 통계 진행 모델 (보정 대상)

테이블마다 핸드 하나를 이렇게 굴린다. 모든 값은 실제 진행 측정에서 보정한다.

| 요소 | 모델 | 보정 데이터 |
|---|---|---|
| 핸드 길이 | 인원·스트리트 분포에 따른 가상 초 | 실제 진행의 핸드별 elapsed |
| 팟 크기 | 블라인드·앤티·유효 스택(bb)에 따른 분포 | 핸드별 팟/bb |
| 올인·쇼다운 | 유효 스택 깊이별 빈도 | 핸드별 올인 여부 |
| 승자 | 참가자 중 실력(프로필)에 가중한 확률 | 선수 실력 vs 칩 증감 |
| 버블 감속 | 남은 인원이 ITM 근처면 올인·탈락 빈도 감소 | 버블 구간 탈락 속도 |
| H4H·파이널 | 실제 진행과 같은 동기화 규칙 | — |

결정적이다: 대회 시드 + 테이블 + 핸드 번호로 만든 로컬 난수만 쓴다.

## 7. 켜기 전 검증 (통과 조건)

같은 포맷·같은 시드 묶음에서 실제 진행 N개와 통계 진행 N개를 비교한다(포맷마다 N≥10 목표).

1. 시간대별 남은 인원 곡선 — 각 시각의 분포가 통계적으로 구분되지 않을 것(KS 검정 등)
2. 스택 분포 — 지니계수, 칩 리더 비중, 하위 10% 스택(bb)
3. 버블 근처 탈락 속도, ITM 도달 시각
4. 대회 전체 길이
5. 넘겨받기 — 칩 보존, 탈락 순서·상금 1회 지급, 넘겨받은 뒤 실제 엔진 오류 0
6. R2 기준선 불변

하나라도 실패하면 켜지 않는다. 결과는 evidence JSON 과 PNG 로 남긴다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 통계 진행이 부자연스러움 | §7 통과 전에는 켜지 않음. 운영 중 지표 이상이면 킬 스위치 |
| 한 대회 안에 실제·통계 구간이 섞여 설명이 어려움 | 구간 기록(§2-6). 대회 결과 화면에 숨기지 않음 |
| 통계 구간의 핸드 기록이 없음 | 관전 모드가 없으므로 노출되지 않음. 관전을 만들면 관전 테이블은 관찰된 테이블로 실제 진행 |
| 봇의 상대 기억(Book)이 통계 구간에서 갱신 안 됨 | 사람과 같이 친 기록은 실제 테이블에서만 생기므로 HERO 관련 기억은 그대로 |
| 보정값이 낡음(엔진·GTO 변경 뒤) | 엔진이 바뀌면 보정 데이터 재수집 + §7 재검증을 필수로 함 |

## 9. 진행 순서

1. **보정 데이터 수집** — 실제 진행 측정 도구(대회 길이 측정)를 확장해 핸드 단위 기록을 남긴다.
2. **coarse_sim.py + field_backend.py** — 기본 `real` 로 두고 추가만 한다.
3. **오프라인 검증(§7)** — 통과 결과를 보고 사용자 승인.
4. **hybrid 켜기** — 승인 후 설정으로 켠다.
5. **로비 정보** — 순위·평균 칩·진행 시간·레벨(오프스크린 레벨 값 갱신 문제 포함)은 두 모드 공통으로 만든다.

## 10. 사용자 결정 필요

- 기본 모드: 당분간 `real`(지금 그대로) / 검증 통과 후 `hybrid`
- 관찰 범위: HERO 테이블만 실제(추천) / HERO 가 참가한 대회 전체를 실제

## 11. 사용자 결정 (2026-10-06)

1. **기본 모드는 `real`.** 검증(§7)을 통과하기 전에는 지금 실제 진행 그대로다.
2. **관찰 범위는 HERO 테이블만.** HERO 가 참가한 대회라도 다른 테이블은 통계 진행이다.

### 11.1 테이블 이동 요구 (문제 없어야 함)

HERO 가 옮겨 가는 경우와 봇이 HERO 테이블로 옮겨 오는 경우 모두, 실제 진행만 쓴 것과
구분되지 않아야 한다.

- **통계 테이블도 테이블 상태를 실제와 똑같이 유지한다:** 좌석 번호, 딜러 버튼 위치,
  블라인드를 낼 차례, 핸드 수, 테이블별 가상 시각. 칩만 굴리면 안 된다.
- **HERO 이동(밸런싱·테이블 깨짐):** 기존 밸런싱 규칙과 시점(완료 핸드 경계) 그대로 옮긴다.
  도착한 테이블은 다음 핸드부터 실제 진행이다. 떠난 테이블은 그 핸드가 끝난 뒤부터 통계 진행이다.
  도착 테이블의 버튼·블라인드 순서는 통계 구간에서 이어져 온 값을 쓴다(새로 정하지 않는다).
- **봇 도착(통계 테이블 → HERO 테이블):** 그 봇의 성향·프로필·틸트·상대 기억은 필드에 있는
  그대로 이어진다. 칩은 통계 구간에서 바뀐 값이다. 도착 시점·좌석은 기존 밸런싱 규칙 그대로다.
- **검증 항목(§7 추가):** 이동 전후 칩 보존, 버튼·블라인드 순서 연속, 좌석 중복 없음,
  이동한 봇의 프로필·기억 보존, HERO 이동 직후 첫 핸드가 실제 엔진으로 정상 진행.

### 11.2 핸드포핸드·파이널 직전의 "다른 테이블이 진행 중인" 느낌

- **H4H(버블)·파이널 직전(테이블 2개 이상 남은 상태):** HERO 테이블의 핸드가 끝나도 다른 테이블이
  그 핸드를 끝낼 때까지 기다린다. 기다리는 시간은 통계 테이블들이 뽑은 핸드 길이(실제 진행에서
  보정한 분포) 중 가장 늦은 끝 시각까지다. 즉시 넘어가지 않는다.
- **평소 구간:** 다른 테이블의 탈락·남은 인원·평균 칩 변화도 통계 테이블의 가상 시각에 맞춰
  조금씩 반영된다(한꺼번에 튀지 않는다).
- **화면:** 기다리는 동안 "다른 테이블 진행 중(핸드포핸드)" 같은 상태를 보여 준다. 대기 시간은
  난수로 꾸미지 않고 위의 통계 테이블 핸드 길이에서 나온다.
- **검증 항목(§7 추가):** H4H 대기 시간 분포가 실제 진행의 H4H 대기 시간과 구분되지 않을 것.

### 11.3 결정 (2026-10-07)

- **핸드포핸드(테이블 3개 이상):** 통계 테이블이 그 핸드의 가상 길이에 비례해 늦게 끝난다
  (`coarse_sim.H4H_DELAY_PER_SECOND` 0.06초/초, 상한 3초 — 45초 핸드 → 2.7초). HERO 가 그 대회에
  앉아 있을 때만(관전자 없는 오프스크린 대회는 지연 없음). 다른 테이블은 병렬로 돌므로 HERO 가
  느끼는 대기는 가장 늦은 테이블의 지연이다. 시간 규칙·가상시계 코드는 건드리지 않았다.
- **파이널 직전(남은 인원 ≤ 2테이블):** 통계 진행을 쓰지 않고 실제 엔진·가상시계로 돈다
  (`coarse_sim.COARSE_MIN_TABLES` = 3, 대회 전체 문맥의 남은 인원으로 판정 — 워커는 자기 테이블만
  받으므로 테이블 수를 직접 셀 수 없다).
- 결과: 스탠다드(99명)는 머니 버블(약 15명)이 2테이블 이하라 버블 H4H 가 실제 엔진으로 돈다.
  통계 H4H 지연은 딥처럼 버블이 3테이블 이상에서 오는 포맷에서 쓰인다.

검증(`tools/verify_observed_field.py`): turbo 377 통계 핸드·29 이동, standard 1779 통계 핸드·86 이동,
불변식 위반 0, 2테이블 이하 통계 핸드 0. verify_scheduled_ui(hybrid, 봇 60) PASS.
