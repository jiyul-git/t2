# 토너먼트 구조 이슈

시간 모델·인간모델과 별개인 대회 구조 문제를 모은다. 여기 올라간 항목은 아직 고치지 않았다.

## TS-1 블라인드가 20레벨에서 멈춘다 (등록 2026-10-05, 2026-10-06 수정)

**현상**: `table.BLINDS` 는 20레벨(15,000/30,000)까지만 있고, 레벨 계산이 전부 `min(..., len(BLINDS))` 로
상한에 묶인다. 그 뒤로는 블라인드가 오르지 않는다.

**영향 범위 — 시뮬만이 아니다**: 같은 표를 실제 게임 경로가 쓴다.
- `fieldsim.Field.advance_level` (`fieldsim.py` 1073·1076행, 핸드 기준·가상시계 기준 둘 다)
- `fieldsim` 블라인드 조회(586행), `live.level`(80행), `table.Table`(60·64행)
- `tournament_store` 시작 스택(171행: `start_bb × BLINDS[0]`)
- `formats.blind_schedule` 은 상승률로 표를 다시 만들 수 있지만 `tourney.py` 만 쓴다.

**관측(타이밍 외부 검증 K.7, 300명 × 3시드)**: 300명 × 30,000칩 = 900만 칩. 10명 이하에서 평균 30bb 이상이고,
파이널 결정의 72~83% 가 40bb+ 이며 이 상태가 642~1,321핸드 이어졌다. `formats.MAX_ENTRIES` = 1000 이면
파이널 평균이 100bb 근처까지 깊어진다. 일반 대회(10분 레벨)에서 20레벨은 약 200분 지점이다.

**왜 문제인가**: 파이널이 수백~천 핸드 동안 딥스택으로 정체되면 실제 토너먼트 진행(대회 길이,
숏스택 압박, ICM 결정의 빈도) 자체가 왜곡된다. 시간 모델의 final 구간 수치도 이 영향을 받는다
(K.7: final 일반형 TB 1.3초/시간 < ITM 4.3).

**후속**: 표를 늘리거나 `formats.blind_schedule` 의 상승률로 레벨을 계속 생성하는 쪽이 후보다.
구조 결정은 사용자 몫. 고친 뒤 final-table 타이밍을 다시 검산한다(TIME_SYSTEM_DESIGN §L).

**수정(2026-10-06, 사용자 결정)**: `table.BLINDS` 를 60레벨로 잇는다. 1~20레벨은 그대로이고, 21레벨부터
BB 40k·50k·60k·80k·100k·120k·160k·200k·300k 를 10배씩 반복(레벨당 평균 약 1.28배, SB=BB/2).
모든 `min(..., len(BLINDS))` 상한이 표 길이를 따르므로 실제 게임·시뮬 경로가 함께 바뀐다.
R2 기준선(e04c7e88/6dc97c62)은 20레벨에 닿지 않아 불변. 포맷별 대회 길이·CPU 실측은 진행 중
(turbo 45명: 1시간 40분, CPU 291초). 오프스크린 진행 필드의 저장 `level` 값이 갱신되지 않는 문제를
발견 — 핸드 블라인드는 테이블 계산 안에서 맞게 쓰이지만 로비 표시용으로 고쳐야 한다.
