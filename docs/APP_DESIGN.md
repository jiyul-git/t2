# 안드로이드 앱 + 개인 계정 설계

지금 T2는 각자 폰의 털묵스에서 서버를 띄우고 브라우저로 `127.0.0.1:8766`에 접속한다. 이것을 **온라인 서버 하나 + 안드로이드 앱**으로 바꾼다. 지인 몇 명이 각자 계정으로 로그인하고, 칩·설정·메모·기록은 계정마다 서버에 남는다.

## 1. 정해진 것

- 엔진은 서버에서 돈다. 앱은 화면만 보여준다.
- 사용자는 지인 몇 명. 플레이스토어에 올리지 않고 APK 파일로 나눠 설치한다.
- **로그인과 계정 만들기는 구글 계정으로 한다.** 처음 구글로 로그인하면 계정이 생긴다.

## 1-1. 이미 해 둔 것 (`test-online` 브랜치, 2026-10-05, 보류 상태)

자세한 내용은 그 브랜치의 `docs/ONLINE_HANDOFF_20261005.md`에 있다.
- `online_server/`: FastAPI 서버, 9인 게임 생성·진행, 터치용 임시 화면.
- `online_server/auth.py`: Firebase ID 토큰을 검증하는 코드(구글 로그인용)와 개발용 토큰. 클라이언트가 보낸 사용자 ID는 믿지 않는다.
- **사람 둘이 같은 토너먼트에 참가하는 시험판:** 다른 테이블에서 시작하고, 각자 자기 카드만 보이고, 칩 합이 보존되는 것까지 검증했다(`tools/verify_duo_online.py`).
- **못 끝낸 것:**
  - 한 사람이 접속을 끊어도 대회가 멈추지 않게 하기(자리 비움 규칙).
  - 영구 계정 저장소.
  - 지금의 다듬어진 `ui/web` 화면 쓰기.
  - 배포.
- 그 브랜치는 master보다 216커밋 뒤처져 있어서 그대로 합칠 수 없다.

**이번 설계에서 쓰는 것:**
- `auth.py`의 Firebase 토큰 검증 방식과 "클라이언트 ID를 믿지 않는다" 원칙은 게이트웨이로 옮겨 쓴다.
- 사람 여럿이 한 대회에 같이 들어가는 기능은 2단계로 미룬다. 1단계는 각자 자기 대회를 한다(지금 혼자 하는 방식 그대로, 계정만 분리).

## 2. 구조

```
[안드로이드 앱(WebView)] ──HTTPS──> [게이트웨이] ──> 사용자별 게임 서버 프로세스
                                     로그인·세션        ui_server.py (기존 그대로)
                                     프로세스 관리        데이터: data/users/<id>/
```

### 왜 사용자마다 프로세스를 따로 띄우나

`ui/server/ui_server.py`는 게임 상태를 전역 하나로 들고 있다(HERO 한 명, 시계, 워커). 여러 사람을 한 프로세스에서 받으려면 서버 전체를 다시 짜야 하고, 그동안 검증된 진행 로직을 건드리게 된다. 대신 사용자마다 지금 서버를 그대로 하나씩 띄운다.
- 엔진·UI 코드는 거의 바꾸지 않는다.
- 지갑·기록이 폴더 단위로 완전히 분리된다. 지금의 개인 데이터 보호 규칙(`personal_data.py`)도 그대로 쓴다.
- 지인 몇 명이라 프로세스 몇 개는 문제없다. 쉬는 사용자의 프로세스는 내려 둔다.

### 게이트웨이 (`server/gateway.py`, 새로 작성, 표준 라이브러리만)

- **구글 로그인:** Firebase Authentication(무료)을 쓴다.
  - 앱(또는 브라우저)에서 구글 계정을 고르면 Firebase가 ID 토큰을 준다.
  - 게이트웨이가 그 토큰을 검증하고(`test-online`의 `auth.py` 방식, `firebase-admin`), 구글 고유 ID(`uid`)로 사용자 폴더를 정한다.
  - 처음 보는 `uid`면 새 계정(새 지갑)을 만든다.
- **허용 목록:** 지인만 쓰도록 들어올 수 있는 구글 이메일 목록을 서버에 둔다. 목록에 없으면 "초대되지 않은 계정"으로 막는다.
- **세션:** 검증에 성공하면 세션 쿠키(HttpOnly, Secure, SameSite=Strict, 30일)를 준다. 이후 요청은 쿠키로 확인한다.
- **프록시:** 로그인한 요청을 그 사람의 게임 서버로 넘긴다. 게임 진행은 `application/x-ndjson`으로 한 줄씩 흘려보내므로 응답을 모아 두지 않고 바로바로 전달한다.
- **프로세스 관리:**
  - 첫 요청에 그 사람의 서버를 띄운다(`127.0.0.1`의 빈 포트, `T2_DATA_DIR=data/users/<id>`).
  - 30분 동안 요청이 없으면 내린다.
  - 진행 중인 토너먼트는 기존 저장·재개 기능으로 이어간다.
  - 동시에 띄울 수 있는 수를 제한한다(기본 4).
- **로그인 화면·가입 화면:** 로비와 같은 디자인으로 만든다.

### 설정을 서버에 저장

지금 덱 색, 내 캐릭터, 플레이 키는 브라우저 `localStorage`에만 있어서 폰을 바꾸면 사라진다. 기존 서버에 `/api/profile`(GET/POST)을 추가해 `data/users/<id>/profile.json`에 저장한다. `localStorage`는 빠른 표시용 캐시로만 남긴다(메모가 이미 이 방식이다).

## 3. 안드로이드 앱 (`android/`)

- Kotlin 액티비티 하나에 WebView 하나. 서버 주소를 열고 쿠키를 유지한다.
- 구글 로그인은 WebView 안에서는 구글이 막기 때문에, 앱 쪽 구글 로그인(Credential Manager)으로 ID 토큰을 받아 Firebase 토큰으로 바꾼 뒤 게이트웨이에 넘긴다.
- 주소창이 없는 전체 화면, 뒤로 가기 처리, 연결이 끊겼을 때 다시 시도하는 화면, 앱 아이콘을 넣는다.
- 빌드는 GitHub Actions가 한다. 저장소에 올리면 APK가 만들어지고, 그 파일을 받아서 설치한다. 서명 키는 저장소 비밀값에 둔다.
- 화면은 웹 그대로라, 앞으로 UI를 고치면 앱을 다시 설치하지 않아도 반영된다.

## 4. 서버를 어디에 둘까 (결정 필요)

| 선택지 | 비용 | 특징 |
|---|---|---|
| **오라클 클라우드 무료 등급** (추천) | 0원 | ARM 4코어·24GB 평생 무료. 가입할 때 카드 등록만 필요하다(과금 없음). 항상 켜져 있다. |
| 집 PC 또는 안 쓰는 폰 + Cloudflare Tunnel | 0원 | 내 기기를 서버로 쓴다. 기기를 끄면 접속이 안 된다. |
| 유료 VPS(국내·해외) | 월 5천~1만 원 | 가장 간단하고 안정적이다. |

- **HTTPS:** 어느 쪽이든 필요하다. Cloudflare Tunnel을 쓰면 인증서와 포트 열기 없이 해결된다.
- **도메인:** 고정 주소가 필요하면 연 1~2만 원이 든다. 없으면 Cloudflare 무료 주소를 쓴다.

## 5. 보안·운영

- 게임 서버 프로세스는 `127.0.0.1`에만 열고, 밖에서는 게이트웨이만 보이게 한다.
- 사용자 폴더는 다른 사용자 프로세스가 읽을 수 없게 권한을 둔다.
- **관리 스크립트:** 허용 이메일 추가·삭제, 사용자 목록, 매일 백업(`data/users`를 압축해 보관).
- **Firebase 프로젝트:** 사용자가 직접 만든다(무료, 구글 계정으로 5분). 프로젝트 ID와 웹 설정값만 서버 설정에 넣는다.
- **기존 털묵스 칩 옮기기:** 지금 털묵스에 있는 내 칩·기록은 한 번만 내 계정으로 옮긴다. 기존 지갑 이동 규칙을 따라, 덮어쓰지 않고 옮긴다.

## 6. 진행 순서

1. `/api/profile`: 설정을 서버에 저장한다. 기존 서버만 고치고 털묵스에서도 바로 쓸 수 있다.
2. 게이트웨이: 구글 로그인 검증·허용 목록·세션·프록시·프로세스 관리. Firebase 없이 시험할 수 있게 개발용 로그인도 둔다(`auth.py`의 dev 모드처럼, 공개 서버에서는 꺼짐), 그리고 시험(동시 사용자 2명이 서로의 칩을 못 보는지, 스트리밍이 끊기지 않는지, 오래 쉬면 내려갔다가 다시 이어지는지).
3. 배포 스크립트: 서버에 설치, 자동 재시작, Cloudflare Tunnel, 백업.
4. 안드로이드 앱: WebView 셸과 GitHub Actions APK 빌드.
5. 내 털묵스 칩을 내 계정으로 옮기기.

1~2는 서버 없이 이 저장소에서 만들고 시험할 수 있다. 3부터는 서버 위치가 정해져야 한다.
