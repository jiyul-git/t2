# ft60: 클래스별 고정 값 표 vs 손패×손패 행렬 끝점 — 설계 검토 (2026-11-10, 소스 읽기 + 저장된 행렬 확인, 새 풀이 없음)

## 현재 엔진이 끝점 값을 쓰는 방식 (vendor gtopen `crates/solver/src/preflop/mod.rs` terminal_value, `t2cont.rs`)
- 표가 있는 헤즈업 끝점: `out[h] = prob × (gross[h] − invested)`. `gross[h]` 는 169개 고정 숫자이고, 상대 레인지에는 **전혀 반응하지 않는다**. 상대 레인지는 `prob`(상대 도착 질량의 곱)으로만 들어간다(t2cont.rs 머리말에도 "A table does not react to the opponent's current reach").
- 표가 없는 끝점: `eqs_vs_dist(dist, ..)` 로 상대 현재 분포 `dist`(= reaches/합) 에 대한 169×169 승률을 매번 계산하므로 레인지에 반응한다. 즉 엔진은 이미 "손패 대 분포" 형태를 지원하고, 표 끝점만 그 형태가 아니다.
- 그래서 표 값은 "표를 만들 때의 상대 레인지" 에서만 두 자리 합이 팟이 된다. 트리가 풀리며 레인지가 이동하면 합이 어긋난다(40bb 검사: 30/37 끝점 > 0.5bb, 3벳 행렬 끝점 27개 전부. ft60 1단계: V0 를 1단계 레인지로 재면 합−팟 중앙값 +5.0bb).

## 지금의 행렬 끝점(matrix_sums)은 어디에 쓰이나, 왜 그것도 어긋났나
- 보드 세션이 끝점마다 `matrix_sums.npz` (자리별 Σw·c⊗c·M, Σw·c⊗c; 169×169) 를 올린다. collect 가 `M = num/den` (A∪B 평균) 을 만들고, **그 끝점 입력(term) 파일의 상대 도착 분포 `dist` 를 곱해** 클래스별 벡터 `V = M @ dist` 로 접는다(ft60.py collect: `M[pos]['AB'][:, use] @ dist[use]`).
- 트리에 들어가는 것은 이 벡터뿐이다(`tables/node*.json` 의 `gross[169]`). 행렬은 접는 순간 버려진다. 그래서 행렬 끝점도 벡터 끝점과 똑같이 "접을 때의 레인지" 에서만 일관되고, 트리 레인지가 이동하면 어긋난다.

## 확인한 사실 (저장된 1단계 행렬, 3벳 행렬 끝점 27개)
- 두 자리 행렬은 손패 쌍마다 합이 팟이다: |M_A[h][j] + M_B[j][h] − pot| 의 끝점별 중앙값 0.0000, 최대 0.0002bb. 행렬 쌍이 채워진 비율 중앙값 1.00.
- 따라서 행렬을 트리 안에서 `gross[h] = Σ_j dist[j]·M[h][j]` (dist = 그 순간의 상대 도착 분포) 로 쓰면, 합이 팟이라는 성질이 **어떤 레인지에서도** 자동으로 성립한다(레인지 가중 합 = Σ p_h q_j (M_A[h][j]+M_B[j][h]) = pot).

## (1) 행렬 끝점을 트리에 직접 넣는 것: 가능, 변경은 엔진 쪽
- t2_pf_solve 자체는 손대지 않는다(t2_pf_solve.rs 는 풀이 드라이버일 뿐). 바꾸는 곳은 `t2cont.rs`(표에 선택 필드 `matrix` 169×169 per seat 읽기, 검증) 와 `terminal_value` 의 표 분기(약 10줄: 상대 분포 정규화 후 `Σ_j dist[j]·M[h][j]`). 표에 `matrix` 가 없으면 지금과 비트 동일하게 동작하도록 한다(0·1단계 재현성 유지).
- 비용: 시간 — 표가 없는 끝점이 이미 매 반복 169×169 `eqs_vs_dist` 를 하므로 같은 규모(행렬 끝점 27개 × 자리 2, 반복당 수만 flop 단위), 전체 트리 반복 시간에 거의 영향 없음. 메모리 — 끝점 40개 × 자리 2 × 169² × 4B ≈ 9MB.
- 위험: ① 행렬은 보드 풀이 때 레인지 아래에서 균형인 플랍 전략으로 구한 것이라 레인지가 많이 바뀌면 M 자체도 달라진다(1차 보정이지 정확한 것은 아님). ② 보드 풀이 레인지 밖 클래스(`matrix_opp_classes` 외, den=0 → NaN)가 트리 레인지에 새로 나타나면 값이 없다 → 그 칸은 정적 승률(`eqs`)로 대체하는 규칙이 필요하다. ③ 행렬이 없는 끝점(헤즈업 단일 레이즈 팟 13개)은 보드 풀이에서 행렬을 내보내지 않았으므로 이 방식의 효과가 없다(벡터 유지, 또는 그 끝점도 행렬 모드로 다시 풀어야 함 — 보드 시간 증가). ④ 문서에 "행렬 지원은 엔진 기능 추가 = 별도 승인 사항" 으로 적혀 있다.
- 2단계 이후 흐름이 바뀐다: 새 표 = 행렬(혼합 0.5·M_T + 0.5·M_V 도 쌍마다 합이 팟이므로 성질 유지). D 는 "접은 벡터" 가 아니라 현재 레인지에서 `Σ M·dist` 로 비교 가능.

## (2) 대안: 섞기 비율(알파)을 낮추기
- 섞기 비율은 진동 폭을 줄일 뿐, 불일치의 원인(고정 값 표가 레인지 이동에 반응 안 함)을 없애지 못한다. 고정점에서는 레인지가 안 움직여 불일치가 사라지지만, 거기까지 가는 단계 수가 늘어난다. 1단계 진단: 처음 표가 생긴 끝점은 알파 1.0 점프 후 V 가 45% 되돌아오는 패턴이라, 첫 갱신만 0.5 로 줄여도 진폭은 반으로 준다. 비용: 단계당 풀이 약 10~20시간(트리) + 보드 세션 20개 × 약 6시간. 단계 수가 2배면 며칠 단위로 늘어난다.
- 합만 팟으로 맞추는 투영(2단계에서 적용)은 상수 이동이라 클래스별 모양은 못 고치고, 이동한 레인지에서 다시 어긋난다. 임시방편이다.

## 추천
1. 엔진에 선택적 `matrix` 지원을 넣는다(표에 `matrix` 가 없으면 기존과 비트 동일). 행렬 끝점 27개부터 시작하고, 행렬이 없는 끝점은 벡터 유지. 구현 약 50~100줄, 검증은 (a) 표 없음/벡터 표에서 0·1단계 풀이와 비트 동일, (b) 행렬 표에서 임의 레인지의 두 자리 합 = 팟 단위 시험, (c) 같은 1단계 데이터로 트리를 다시 풀어 레인지 이동 후 D/U 가 줄어드는지(보드 새로 안 풀고 볼 수 있는 1차 확인 불가 — 레인지가 바뀌면 M 도 바뀌므로 결국 보드 한 단계가 필요).
2. 병행해서 알파는 첫 갱신 0.5 로 낮추는 안을 쓸 수 있다(행렬 구현 전 임시).
3. 승인 필요: 엔진 변경(별도 승인 사항), 행렬 없는 끝점 13개를 행렬 모드로 다시 풀지 여부.
