# Poker decision / concept inspection checklist v1

Purpose: freeze the **target inspection grid before changing code**.

This checklist is deliberately not derived only from current concept names.  Otherwise accidental
aliases and missing concepts would be preserved as if they were design.  Each row is checked against
the actual call path and then classified.

Status legend:

- OK = concept and decision path match the intended meaning
- SHARED = one concept intentionally or accidentally serves multiple strategic meanings/streets
- LEAK = a concept from another street/domain affects this row through an alias/compatibility field
- DUP = the same action can be generated by more than one decision path
- MISS = strategically distinct row exists but has no corresponding concept/path
- REVIEW = do not split/add until semantics justify it
- SHADOW = measured but intentionally inactive

## Layer rule

Do not make one concept do all three jobs.

1. **Motive / strategic understanding** — why take the line? (bluff, semibluff, thin value, etc.)
2. **Execution skill / action form** — how can it be expressed? (check-raise, overbet, blockbet, etc.)
3. **Perception / calculation** — what information can the player use? (range read, sizing tell,
   blocker, fold equity, pot odds, etc.)

A composite action should normally combine these layers instead of inventing a new monolithic
concept such as `river_bluff_checkraise`.

## F. Confirmed cross-domain leaks / compatibility hazards to inspect first

1. `preflop.defend_decision()` reads generic `thin_value`, which aliases to
   `thin_value_turn`.  A postflop thin-value skill currently changes the preflop 3-bet/call mix.
2. `persona.derive()['value']` is set from **checkraise_flop** only, but `profile['value']=='xr'`
   later changes trap taste and value-bet frequency on later streets.
3. `_allowed(..., plan='trap')` asks for generic `checkraise`, which aliases to
   **checkraise_flop**, even when the live trap is on turn/river.
4. `bluff_fear` and `hero_call` biases always read **bluffcatch_river**; those biases are then
   used in earlier-street call decisions as well.
5. Actual check-raises can be produced by generic `decide_response` before
   `checkraise_decision`, so the declared check-raise skill is not guaranteed to govern the action.
6. Current opponent book tracks street-specific **fold-to-bet**, but not the distinct event
   **bet-then-fold-to-raise**.  A river bluff check-raise model cannot directly know the latter yet.
7. `tricky` is derived from checkraise_flop/trap/overbet but has no runtime consumer; treat as
   display/compatibility debt, not a strategic concept.

## Inspection order

For every row:

1. locate all producers/consumers;
2. classify it as plan/motive, execution, or perception;
3. determine whether street sharing is semantically legitimate;
4. find aliases/derived compatibility fields that leak another concept in;
5. find duplicate action-producing paths;
6. only then mark: keep / split / add / remove compatibility read / reroute;
7. after taxonomy is locked, run targeted counterfactuals;
8. only after that redo prior calibration.

No LOADING/SPREAD calibration is accepted while any LEAK/DUP/MISS row above is unresolved.
